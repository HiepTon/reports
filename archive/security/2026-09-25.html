Summary

A recent phishing campaign is utilizing a single, complex URL designed to confuse security controls by exploiting differences in how various tools parse URL standards. The URL incorporates a 'userinfo' field to bypass reputation filters, a hyphenated hostname to evade strict validators, and the victim's own email address in the path to deceive naive parsers. Analysis

This technique demonstrates that attackers are increasingly focusing on the 'seams' between different security products, exploiting inconsistencies in how parsers handle RFC standards. Defenders should audit their URL filtering and sandboxing solutions to ensure they adhere to strict standards (like WHATWG) rather than relying on loose, regex-based extraction. Hunting efforts should focus on identifying URLs containing multiple '@' symbols, non-standard hostname formatting, or internal email addresses within the URL path.

The Truth about GET and HTTP Standards, (Tue, Sep 22nd)

Summary

This article discusses the ambiguity in HTTP standards regarding whether GET requests should contain a message body. Testing various web servers reveals inconsistent behavior: some servers (like Apache) accept and process the body, while others (like NGINX or Python's built-in server) ignore it, and some (like lighttpd) reject the request entirely. This inconsistency can lead to security bypasses or unexpected application behavior if developers rely on assumptions about how GET requests are handled.

Analysis

The lack of standardization in handling GET request bodies creates a potential surface for request smuggling or WAF bypass attacks, where a security device might interpret the request differently than the backend server. Security teams should ensure that their web application firewalls and load balancers are configured to explicitly reject GET requests containing bodies, or at least normalize them consistently across the infrastructure. Developers should avoid using GET requests for operations that require a body payload.
